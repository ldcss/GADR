# GADR — Architecture Decision Records Generation

This repository contains the scripts and data used to generate Architecture Decision Records (ADRs) from meeting transcripts and to compare different generation strategies.

This artifact is self-contained and organized so that another researcher can understand the inputs, reproduce the runs, and inspect the generated outputs.

Access the accepted article here: [GADR_IIER_2026.pdf](https://github.com/user-attachments/files/30288552/GADR_IIER_2026.pdf) and the persistent repository DOI: https://doi.org/10.5281/zenodo.21501560



## Project Structure

```text
├── adrs_json/         JSON files listing the ADR source repositories
├── chroma_db/         Local Chroma database built from the ADR dataset
├── dataset_adrs/      Consolidated ADR dataset used by the retrieval pipeline
├── downloaded_adrs/   ADRs downloaded from the source repositories
├── evaluation/        Evaluation results and comparison tables
├── generated/         ADRs generated by the three approaches
├── constants.py       Transcript given as input to the scripts (fill this in before running)
├── few_shot_adr.py    Few-shot ADR generation script
├── zero_shot_adr.py   Zero-shot ADR generation script
├── research_agent_adr.py  Agentic RAG-based ADR generation script
├── requirements.txt   Python dependencies
└── LICENSE            Project license
```

## Requirements

### Software

- **Python 3.10 or newer** and the ability to create a virtual environment.
- macOS, Linux, or Windows with a working terminal.
- Internet access — all three scripts call remote APIs on every run.
- Roughly 2 GB of free disk space for the dataset, the Chroma database, and the generated outputs.

The Python dependencies are listed in `requirements.txt` (`google-genai`, `langchain_tavily`,
`langchain_text_splitters`, `chromadb`, `langgraph`, `python-dotenv`) and are installed in
step 2 of the Installation section.

### Accounts and API keys

Two credentials are required, and **both are needed by all three scripts** — see the note on
Tavily below.

#### 1. Google Gemini via Vertex AI — `GEMINI_API_KEY` (required)

All three scripts build the model client like this:

```python
from google import genai
client = genai.Client(api_key=gemini_api_key, vertexai=True)
```

The `vertexai=True` flag routes every request to **Google Cloud Vertex AI**, *not* to the
Gemini Developer API. This is the single most common reason a run fails: **an API key created
in Google AI Studio will not work here.** You need a **Vertex AI API key** issued from a Google
Cloud project:

1. Sign in to the [Google Cloud Console](https://console.cloud.google.com/) and select or create a project.
2. Enable the **Vertex AI API** for that project: *APIs & Services → Library → "Vertex AI API" → Enable*. Billing must be enabled on the project.
3. Create the key at [Vertex AI Studio](https://console.cloud.google.com/vertex-ai) (Vertex AI **Express Mode** API key), or via *APIs & Services → Credentials → Create credentials → API key*, restricting the key to the Vertex AI API.
4. Copy the key. This is the value of `GEMINI_API_KEY` in your `.env` file.

Despite the variable name, the value must be a **Vertex AI** key.

#### 2. Tavily web search — `TAVILY_API_KEY` (required)

Create a free account at [tavily.com](https://tavily.com) and copy the API key from the
dashboard. The free tier is enough to reproduce the runs.

`research_agent_adr.py` uses Tavily to research each decision. `zero_shot_adr.py` and
`few_shot_adr.py` never perform a search, but they still construct `TavilySearch(...)` at
import time — so **they also fail at startup if `TAVILY_API_KEY` is missing.**

### Models used

| Model ID | Where it is used |
| --- | --- |
| `gemini-3.1-pro-preview` | Every explicit call: ADR generation, decision extraction, critique, re-ranking |
| `gemini-3-flash-preview` | Default of `get_model_response(...)`; transcript translation in `research_agent_adr.py` |

These IDs are hardcoded in the `model_name` arguments of each script. If your Google Cloud
project cannot serve those preview models (symptom: a `404 NOT_FOUND` / "model not found"
error), replace them with a model your project does have access to — for example
`gemini-2.5-pro` and `gemini-2.5-flash` — in the `model_name=` arguments and in the
`get_model_response` default of the script you are running.

## Installation

**1. Clone the repository and create a virtual environment.**

```bash
git clone https://github.com/<user>/GADR.git
cd GADR
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
```

**2. Install the dependencies.**

```bash
pip install -r requirements.txt
```

**3. Create the `.env` file and fill in both keys.**

```bash
cp .env.example .env
```

Then edit `.env` so it contains your own values:

```dotenv
GEMINI_API_KEY="<your Vertex AI API key>"
TAVILY_API_KEY="<your Tavily API key>"
```

Every script loads this file with `python-dotenv` and reads exactly these two variable names
via `os.getenv`. Keep the names as they are. `.env` is listed in `.gitignore`, so your keys are
not committed.

**4. Verify the Gemini/Vertex key before running the pipeline.**

This isolates an authentication problem from a pipeline problem. It builds the same client the
scripts build:

```bash
python3 -c "
from dotenv import load_dotenv; import os
from google import genai
load_dotenv()
client = genai.Client(api_key=os.getenv('GEMINI_API_KEY'), vertexai=True)
print(client.models.generate_content(model='gemini-3.1-pro-preview', contents='Say OK').text)
"
```

If this prints `OK`, the key and the model are both usable. If it raises an authentication or
permission error, the key is almost certainly an AI Studio key rather than a Vertex AI key
(see Requirements). If it raises a `404` for the model, pick a model your project can serve.

## Working Example

`constants.py` is shipped with an **empty** transcript, and the meeting transcripts analysed in
the paper are **not distributed with this repository** (they contain identifiable participant
speech — see Data and Ethics). Running a script without filling in `constants.py` first sends an
empty transcript to the model and produces no meaningful ADR. Use the example below to perform a
complete end-to-end run.

**1. Put a transcript in `constants.py`.** Replace the file's contents with:

```python
#transcript that is automatically used by the selected approach

transcript = """
Ana: We need to settle the datastore for the reporting service today.
Bruno: Postgres is the obvious candidate. We already run it for the main API, the team knows it,
and the reporting queries are relational anyway.
Ana: We did consider MongoDB, but the reports are all joins across five tables. Document storage
would just push the joins into application code.
Bruno: Agreed. Postgres it is, on the managed instance we already pay for.

Ana: Next, authentication for the new admin portal.
Carla: I'd rather not build our own login. We should delegate to the corporate identity provider
over OIDC. Social login with Google was suggested, but these are internal staff accounts and IT
requires central deprovisioning.
Ana: Then OIDC against the corporate IdP. Sessions stay short-lived, one hour, refreshed silently.
Bruno: That also means we never store passwords, which shortens the compliance review.

Carla: Last item, deployment. The service is small and traffic is spiky, a few thousand requests
a day concentrated at month end.
Bruno: Containers on the existing Kubernetes cluster would work, but we'd pay for idle nodes all
month. A serverless container runtime scales to zero and bills per request.
Ana: Cold starts are the tradeoff, but for internal reporting a two-second first request is fine.
Let's go serverless containers and revisit if latency becomes a complaint.
"""
```

**2. Run one of the approaches.**

```bash
python3 zero_shot_adr.py
```

**3. Expected result.** The script prints its progress and writes one Markdown file per ADR into
the repository root:

```text
--- PROCESSING MEGA-PROMPT (Multi-ADR Extraction) ---
ADR 1 extraída e salva como adr_decision_1.md
ADR 2 extraída e salva como adr_decision_2.md
ADR 3 extraída e salva como adr_decision_3.md
```

Open `adr_decision_1.md` to inspect the generated record. With the transcript above you should
get roughly three ADRs — datastore choice, authentication strategy, and deployment target — each
following the Nygard structure (Status, Context, Decision, Considered Options, Consequences).

`few_shot_adr.py` is run the same way and writes to the same `adr_decision_N.md` filenames.

`research_agent_adr.py` takes noticeably longer and makes many more API calls: it detects the
transcript language and translates it if needed, extracts and critiques the decision list over up
to three refinement iterations, then for each decision queries the bundled Chroma database and
Tavily before generating the record. It names each output after the ADR title, for example
`adr-001-adopt-postgresql-for-the-reporting-service.md`.

## How to Use

The scripts were exported from notebooks and all read the transcript defined in `constants.py`,
so the workflow is always: put a transcript in `constants.py`, then run one script.

| Script | Approach | Requires | Output |
| --- | --- | --- | --- |
| `zero_shot_adr.py` | Single zero-shot prompt | Both API keys | `adr_decision_N.md` in the repository root |
| `few_shot_adr.py` | Same prompt plus two worked ADR examples | Both API keys | `adr_decision_N.md` in the repository root |
| `research_agent_adr.py` | LangGraph agent: translate → extract → critique → retrieve (Chroma + Tavily) → generate | Both API keys and the bundled `chroma_db/` | One `<adr-title>.md` per decision, in the repository root |

The Chroma database in `chroma_db/` is already populated from `dataset_adrs/`, so no ingestion
step is needed. The `ingest_from_sample_data()` call in `research_agent_adr.py` is intentionally
commented out; uncomment it only if you want to rebuild the collection from your own ADR corpus.

Substitute any other meeting transcript by editing `constants.py`. Transcripts in languages other
than English are supported by `research_agent_adr.py`, which translates them before extraction.

### Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Authentication / permission denied on the first model call | The key is a Google AI Studio key. The scripts pass `vertexai=True`, so a Vertex AI API key from a Google Cloud project with the Vertex AI API enabled is required. |
| `404 NOT_FOUND` or "model not found" | Your project cannot serve `gemini-3.1-pro-preview` / `gemini-3-flash-preview`. Replace those IDs in the `model_name` arguments with a model you do have (e.g. `gemini-2.5-pro`). |
| Error mentioning Tavily immediately at startup, even for `zero_shot_adr.py` | `TAVILY_API_KEY` is missing from `.env`. All three scripts construct the Tavily client at import time. |
| The script runs but the ADRs are empty or generic | `constants.py` still holds the empty transcript. Paste a transcript into it as shown in Working Example. |
| `ModuleNotFoundError` | The virtual environment is not active, or `pip install -r requirements.txt` was not run inside it. |

## Data and Ethics

The meeting transcripts used in the study are not redistributed here, because they contain identifiable participant speech. The repository does include the ADR material derived from them (`generated/`, `evaluation/`) as well as the public ADR corpus in `dataset_adrs/` and `downloaded_adrs/`. If you reuse these files, review any applicable privacy, consent, and redistribution constraints before sharing them outside the intended research context.
