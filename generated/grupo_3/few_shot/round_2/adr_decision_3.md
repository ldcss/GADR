# [ADR-003] AWS ElastiCache (Redis) for On-Demand User Session Caching
- **Status**: Accepted
- **Context**: To meet the 3-second SLA for user identification and workout payload delivery during peak hours, the system must avoid querying the primary database for every machine interaction.
- **Decision**: Implement AWS ElastiCache (Redis) to cache user workout data on-demand, predicting and pre-loading data based on user attendance patterns.
- **Considered Options**:
  - *Option 1: Direct transactional database queries.* Rejected because the database cannot guarantee sub-3-second response times under the heavy concurrent read/write load generated by hundreds of active machines at peak hours.
  - *Option 2: Local in-memory cache (e.g., node caching).* Rejected because the backend will be horizontally scaled behind a load balancer, leading to constant cache misses and inconsistent states across instances.
- **Consequences**:
  - *Pros:* Drastically reduces read latency and protects the primary database from read exhaustion; Redis natively serves as the storage backend for BullMQ, consolidating infrastructure requirements.
  - *Cons:* Introduces distributed cache invalidation complexity and adds ongoing costs for the managed ElastiCache instances.
