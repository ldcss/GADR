# [ADR-005] Centralize Data Architecture Around Care "Attendances" as the Main System Bus

**Date:** 2026-05-22

## Status
Accepted

## Context
The platform must support varied home care and telemonitoring clinical scenarios (e.g., palliative care, post-surgical follow-up, elderly risk monitoring) across multiple institutions. The system will handle high volumes of transactional health data and require cross-cutting functionalities like AI-driven risk analysis, tele-assistance scheduling, and notifications. Without a unified data blueprint, there is a severe risk of creating unmanageable "data swamps" and isolated domain silos. High data quality is non-negotiable for accurate clinical analytics and downstream interventions. 

## Decision
We will design the system's core data skeleton entirely around care "attendances" (the distinct home care events and monitoring sessions). This attendance model will function as the enterprise main bus. All auxiliary functionalities—such as AI data analysis, clinical protocol execution, and notification services (via management and query APIs)—will be built as services operating on top of this standardized core data.

## Considered Options
1. **Centralized "Attendance" Data Bus (Selected):** Anchoring the system to the transactional care event. It creates a robust, single source of truth for the primary operation of the platform, enabling standard data quality management and seamless downstream consumption.
2. **Decentralized/Module-Specific Data Stores (Rejected):** Allowing each clinical scenario (e.g., Cuidativa, UFPB) to manage its own raw data structures. Rejected due to the high risk of data fragmentation, which would make implementing shared AI analysis and notification microservices exponentially more difficult.
3. **Static Patient-Profile Centric Base (Rejected):** Modeling the core system strictly around static patient demographic profiles. Rejected because the primary system drivers, clinical triggers, and heavy transactional loads are generated by the active *care events* (attendances), not the static profiles.

## Consequences
* **Pros:**
  * Establishes a standardized architectural blueprint that prevents the accumulation of raw health data from becoming an unusable "data swamp."
  * Ensures uniform data quality management, which is critical for generating accurate, valuable insights in the downstream AI analysis service.
  * Simplifies the development of shared services (e.g., standardizing a universal notification service with unified management and query APIs).
* **Cons:**
  * Requires significant upfront engineering and domain analysis to generalize a single "attendance" model capable of accommodating the unique variables of all four separate clinical protocols.
  * Enforces rigid data validation at the core layer, potentially slowing initial module development by requiring strict adherence to the centralized schema.
